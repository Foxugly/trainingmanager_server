# TrainingManager — audit complet (2026-06-10)

Second passage d'audit profond (backend + frontend), après la résolution de
`AUDIT-2026-06.md` (tous les P0, features E2–E7, CSP phase 1, décisions JWT &
magic-link). Fait par exploration parallèle multi-agents : sécurité backend,
perf backend, UX/Angular frontend, dette technique (2 repos), opportunités de
features. Les items déjà résolus/décidés dans l'audit précédent ne sont **pas**
re-listés.

**Verdict global :** codebase de très haute qualité et disciplinée. Frontend :
zéro violation des conventions interdites (pas de `*ngIf`, `ngClass`, injection
constructeur, `signal.mutate`, `any` hors client généré…), i18n synchronisé à
1165 clés sur les 5 langues (zéro dérive). Backend : autorisation object-level
rigoureuse presque partout. Les trouvailles ci-dessous sont ce qui **reste**.

## 🔴 Sécurité

> **Tous les items de cette section sont RÉSOLUS le 2026-06-10** (P1 IDOR Exercise +
> champ `author`, titre Topic sanitizé, `rel=noopener`, Swagger/docs DEBUG-only,
> docstring `MeView`). Détail conservé ci-dessous.

### ☑ P1 — `ExerciseViewSet` update/delete sautent l'autorisation object-level (IDOR)
- `exercise/views.py` (`ExerciseViewSet`) + `exercise/serializers.py` (`ExerciseSerializer.update`).
- L'audit précédent a durci `RoundViewSet` (`_require_may_mutate` sur update/destroy/clone)
  mais **l'`ExerciseViewSet` analogue n'a pas reçu le même traitement**. Seul gate :
  `IsTrainer` (le caller gère *une* équipe active — pas *cet* exercice).
- La protection fork-on-edit du serializer ne se déclenche que si `usage_count > 1`
  (compte les **rounds**). Un exercice de séance réel vit sur un seul round → `usage_count == 1`
  → garde sautée → `super().update()` en place **sans vérif d'autorisation**. Un trainer du
  même scope sport+langue peut `PATCH /exercises/{id}/` (sans `round_id`) et muter l'exercice
  d'une autre équipe.
- `DELETE /exercises/{id}/` est **totalement non gardé** (pas de `perform_destroy`).
- **Fix (bas risque, sans migration) :** ajouter `perform_update`/`perform_destroy` à
  `ExerciseViewSet` calqués sur `RoundViewSet._require_may_mutate` (résoudre rounds → events →
  exiger que le caller gère une équipe liée) ; appliquer la même vérif sur la branche
  `usage_count <= 1` de `ExerciseSerializer.update`. **→ recommandé en priorité.**

### P2 — Exercices clonés/créés non attribués (pas d'`author`)
- `exercise/models.py` n'a pas de champ `author` (contrairement à `Round`). Conséquence :
  même après le fix P1, les exercices *de bibliothèque* (sans event lié) ne peuvent pas être
  protégés par auteur, et le dedup `get_or_create` fait que les éditions débordent sur toutes
  les équipes qui ont réutilisé la ligne.
- **Fix (migration → supervisé) :** ajouter `Exercise.author` (nullable), le stamper sur
  create/clone/AI-generate, gater la mutation des exercices-bibliothèque sur auteur-ou-staff.

### P2 — Titres de Topic non sanitizés (XSS stockée potentielle)
- `messaging/serializers.py` `TopicSerializer.validate_title` ne fait que `.strip()`, alors que
  `MessageSerializer.validate_content`, les notes et l'HTML AI passent par `sanitize_html`.
- **Fix :** passer le titre par `strip_html(...)` (plein texte = bon modèle pour un titre).

### P2 — `sanitize_html` autorise `<a target>` sans forcer `rel="noopener noreferrer"`
- `tools/html_sanitizer.py` — bleach n'injecte pas `rel="noopener"` automatiquement →
  reverse-tabnabbing via `window.opener` depuis une note/message.
- **Fix :** callback bleach forçant `rel="noopener noreferrer"` quand `target` est présent
  (ou retirer `target` de l'allow-list). Sans migration.

### P2 — Schéma OpenAPI + Swagger UI servis sans condition en prod (info disclosure)
- `django-trainingmanager/urls.py` — `api/v1/schema/` et `api/v1/docs/` montés sans auth et
  indépendamment de `DEBUG`. Toute la surface d'API est énumérable publiquement.
- **Fix :** gater `/schema/` et `/docs/` derrière `IsAdminUser` ou `DEBUG` ; le client typé est
  généré en CI (le drift-guard n'a pas besoin de l'exposition prod).

### P2 (doc) — Docstring `MeView` obsolète vs flux change-email (E7) maintenant live
- `customuser/views.py` — la docstring dit encore "changing the email requires admin
  intervention… deferred to v2". E7 est implémenté. `email` reste `read_only` (pas d'expo) →
  correctif documentaire seulement.

**Catégories vérifiées et saines :** flux auth (anti-énumération, Turnstile fail-closed,
refresh-ownership au logout, salts/TTL des signed-tokens corrects), IDOR sur member/attendance/
rsvp/roti/note/performance/attachment/messaging/program/memberships/join-magic/audit/dashboard/
notifications, mass-assignment bloqué (`is_staff`/`team_quota`/`calendar_token` read-only),
throttling par scope, settings fail-loud + cookies sécurisés + CSP native.

## ⚡ Performance backend

### P1 — Filtres `Attendance.status__code="present"` sans index dédié (chemin chaud stats/recap/RSVP/dashboard)
- `team/views.py` (`_attendance_stats` ×2, `_intensity_stats`, `_volume_stats`),
  `send_weekly_recaps.py`, `dashboard/views.py`. Sur fenêtre 2 ans (`STATS_MAX_SPAN_DAYS=731`),
  `/stats/` lance ce filtre 3×. Les index existants `(event,member)` / `(member,-created_at)`
  ne couvrent pas `status`, et `status__code` force un join + filtre non-indexable.
- **Fix sans migration (shippable) :** résoudre l'`AttendanceStatus.id` "present" une fois et
  filtrer `status_id=<id>` au lieu de `status__code="present"` → utilise un index FK plain et
  évite le join sur chaque appel. **Variante migration (supervisé) :** `Index(["status","event"])`.

### P2 — `notify_many` envoie les emails un par un dans la requête déclenchante
- `notifications/services.py`, appelé par `messaging/views.py` (`_notify_new_message`) et
  `program/views.py`. Un message de chat sur une équipe de 30 athlètes bloque le POST sur 30
  `send_mail` SMTP séquentiels. **Fix :** `send_mass_mail`/connexion unique + envoi après
  `transaction.on_commit` (idéalement file/thread).

### P2 — `EventViewSet` list prefetch + sérialise `equipment_items` (nested) sur chaque ligne
- `event/views.py` — la liste calendrier hydrate l'équipement nested pour 100+ events alors que
  seul le détail en a besoin. **Fix :** gater le prefetch+sérialisation `equipment_items` derrière
  `self.action == "retrieve"` (comme `rounds_detail`).

### P2 — `RsvpViewSet._summary` charge deux querysets membres redondants ; `managed_teams()` ré-évalué 2-3× par requête (member/audit) ; `_topic_recipients` non prefetch.
- Gains mineurs, sans migration : reconstruire `active_members` depuis les memberships déjà
  nécessaires ; mémoïser `managed_team_ids` au niveau vue.

**Déjà bon (vérifié) :** `/stats/` (Count/Sum/annotate DB-side, fenêtre clampée), dashboard,
`rounds_detail` (prefetch retrieve-only), member list, AI notify, RSVP apply — aucune N+1.

## 🎨 Frontend (UX / Angular)

Aucun P0/P1. Très conforme. Findings P2 :

- **`effect()` au lieu de `toObservable→switchMap` pour les fetch filtrés (race condition)** —
  ~7 composants : `programs-list`, `event-roti`, `team-requests`, `member-notes`,
  `programs-detail`, `round-exercises`, `team-place-pool`. Sans annulation in-flight → réponses
  hors-ordre sur changement rapide de filtre. La convention documente `toObservable→switchMap`
  comme préféré (réf. team-discussions). **Fix :** migrer ; supprimer les gardes `loadedForXId`.
- **Footer logo en `<img src>` brut** au lieu de `NgOptimizedImage` (`footer.component.html`).
- **Dashboard `loadMyPerformances()` avale les erreurs** → un échec API rend "aucune perf" sans
  retry. Ajouter un état d'erreur/retry comme les autres sections.
- **Listes admin taxonomie n'utilisent pas `EmptyStateComponent`** (utilisent `pTemplate=emptymessage`)
  — déviation de cohérence visuelle, pas un bug.

## 🧹 Dette technique (par payoff/effort)

**Backend**
1. **[S/élevé] Mixin équipe-manager + `get_team()`** dupliqués dans ~9 vues (6 formes de la
   vérif manager, `get_team()` réimplémenté 5× dont 2 mémoïsées et 2 non). → `TeamScopedViewMixin`.
2. **[S/élevé] 4 modules signed-token quasi identiques** (`magic_link_token`, `email_change`,
   `rsvp/magic_rsvp`, `team/magic_action`). → `tools/signed_token.py` (helper `ColonToken`).
   Supprime l'incohérence où certains `parse` avalent `SignatureExpired` et d'autres le relancent.
3. **[M/élevé] `team/views.py` = 1637 lignes** (6 viewsets + ~10 helpers stats). → scinder par
   classe + extraire `team/stats.py` (fonctions pures, testables hors viewset).
4. **[S/moyen] Boilerplate viewset CRUD admin ×4** (`get_serializer_class` + bloc
   `@extend_schema_view` quasi identiques). → base `AdminFlavorViewSet`.
5. **[S/moyen] `customuser/views.py` = 1316 lignes** (~18 APIView + `DataExportView` à 11
   `_export_*`). → scinder + extraire `customuser/export.py`.
6. **[S/faible] Tests minces** sur `dashboard`, `audit` (branches sécurité-sensibles).

**Frontend**
7. **[S/élevé] ~30 helpers `notify*` toast** copiés dans ~20 composants. → `ToastService`
   (`success/error/unknownError/mutationError`). Supprime ~120 lignes.
8. **[S/moyen] `ModalitiesListComponent` (175 l.) n'a pas eu l'extraction `TaxonomyListBase`**
   (divergence justifiée — nested sous sport — mais ~80% de recouvrement). → `NestedTaxonomyListBase`.
9. **[S/moyen] Formulaires multi-onglets avalent la validation sur onglet caché** (`teams-form`,
   `events-form`) — pas de `markAllAsTouched()` ni de switch vers le 1er onglet invalide au submit.
10. **[M/moyen] 32 endpoints métier typés `Observable<any>`** (gaps schéma, surtout `auth.service`).
    → `@extend_schema(responses=…)` backend + regen.
11. **[S/faible] Dark mode à moitié construit** (3 SCSS avec `:host-context(.dark-mode)`, pas de
    toggle). Finir ou retirer.

**Résolu depuis l'audit précédent :** garde `CanDeactivate` (`unsaved-changes.guard.ts`, branchée
events/programs/teams) — l'audit la listait ouverte. Markers TODO/FIXME/HACK = 0 dans le code écrit.

**Toujours différé (migration → supervisé) :** index manquants (corriger le mismatch
`Program` — la liste ordonne par `name`, pas `updated_at` ; viser `(team,is_active)`),
idempotence `weekly_recaps`, magic-link single-use, swap `bleach→nh3`, + l'`Attendance.status`
index (finding perf P1).

## ✨ Opportunités de features (ancrées dans les modèles existants, hors push/realtime)

Triées par valeur/effort :
1. **[S] ROTI drift** — flag perçu-vs-planifié par athlète (`Roti` + `Event.total`). Signal
   sur/sous-entraînement gratuit. Étend `_assemble_stats`, nouveau panneau team-stats.
2. **[S] Notification PB battu** — sur création `Performance`, comparer au best (member,label)
   en respectant `is_lower_better` → `notify()` + `NotificationType.PB_BEATEN` (enum ouvert, pas
   de migration data).
3. **[S] Timeline historique de roster** — `TeamMembership` garde déjà join/leave ; exposer
   `GET teams/{id}/roster-history`. Permet aussi de corriger le taux de présence post-churn.
4. **[S/M] Rapport fiabilité RSVP** — "going puis absent" (`Rsvp`+`Attendance`), colonne dans la
   liste membres. Réutilise la branche `?member=` du stats.
5. **[S/M] Debrief de séance** — vue consolidée par event (présence + ROTI moyen + RSVP-vs-réel
   + pièces jointes + texte debrief via `Note` coach-only). Pas de migration en variante Note.
6. **[M] Templates de séances** — séance nommée réutilisable instanciable sur n'importe quelle
   date (réutilise `Event`+`RoundViewSet.clone`). Le plus gros gain workflow.
7. **[M] AI "explique cette séance aux athlètes"** — brief plain-language respectant `vis_*`,
   calqué sur `team/ai_review.py` (+ `AIUsage.Endpoint.EXPLAIN`).
8. **[S/M] Détecteur de conflit place/équipement** — `Place` partagé → events chevauchants entre
   équipes ; warning si `equipment_items` ∉ `team.equipment`.
9. **[S/M] Digest email** (PAS realtime) — batch des non-lus messaging/notifs en un email
   programmé, calqué sur le timer weekly-recap.

**Manques produit notés (nouveaux subsystèmes, non proposés — à valider) :** suivi blessures /
indisponibilité athlète ; check-in bien-être/readiness matinal ; contact d'urgence / note médicale
sur `Member` (GDPR — le cadre anonymisation/audit existe déjà) ; le taux de présence stats utilise
le roster *actuel* pour les séances passées (faux après churn — réparable via #3).

## Recommandation de priorisation

- **À faire vite, bas risque, sans migration :** P1 sécurité Exercise (IDOR), P2 titre Topic +
  `rel=noopener`, P2 Swagger/docs gated, perf P1 variante `status_id`. + dette #1/#2/#7 (mixin,
  signed-token, ToastService) — tous S, haut payoff, sans risque sur la prod non supervisée.
- **Migrations groupées (supervisé) :** `Exercise.author`, index `Attendance.status` +
  `Program`, idempotence recaps.
- **Feature quick-win si tu en veux une :** #1 ROTI drift ou #2 PB battu (S, réutilisent
  l'existant).
